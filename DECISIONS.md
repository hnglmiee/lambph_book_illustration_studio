# Decisions

This file records the decisions that actually shaped this project — not a feature list, not a worklog. Each entry: who proposed it, what the pushback was, where we landed, what it cost.

---

## 1. Postgres + Flyway instead of JSON files or Hibernate auto-DDL

The brief allows JSON files on disk as a legitimate choice for this scope. We went with Postgres instead — the stack is Spring Boot, and JPA plus a real transactional database is the "boring, familiar" choice for that ecosystem. Hand-rolling per-project file locks to satisfy the concurrency requirements (§4.3: no duplicate calls, safe concurrent writes) would have meant more code and more risk than `docker-compose up` plus a migration file. Cost accepted: this requires `docker-compose.yml` and a running container, whereas file-based storage would have needed neither.

On top of that, we chose Flyway-managed migrations (`ddl-auto=validate`) over letting Hibernate auto-generate the schema (`ddl-auto=update`). This wasn't just a preference — it surfaced a real bug: `@ColumnDefault("now()")` only takes effect when Hibernate owns the DDL. With Flyway, it's inert metadata, and Hibernate still inserts an explicit `NULL` for any Java field left unset, rather than omitting the column and letting the database's `DEFAULT now()` apply. This produced a real `null value in column "created_at" violates not-null constraint` failure at runtime. Fixed with `@PrePersist`/`@PreUpdate` callbacks that set timestamps in Java before every insert/update — more explicit, and it doesn't silently depend on which ORM strategy happens to be active.

## 2. Separate `status` and `step_state` columns

A project's progress needs two independent axes: which of the 5 pipeline steps is the *last completed one* (`status`: `CREATED → STYLE_SET → CHARACTERS_GENERATED → PORTRAITS_GENERATED → CHAPTERS_GENERATED → DONE`), and whether the *current* step is idle, running, or failed (`step_state`: `IDLE / RUNNING / FAILED`). A single enum can't express "characters are done, portraits are currently running" — which is exactly the state a page refresh or a retry click has to read correctly. We split it into two columns, plus `step_started_at` (nullable timestamp, used for stale-step detection) and `step_failure_reason` (surfaced to the user on failure). Cost: two fields that have to stay in sync on every transition, and a `RUNNING` state that gets stranded (e.g. the server restarts mid-call) needs an explicit recovery policy — see decision 5.

## 3. Two independent Gemini interaction chains, not one

The pipeline requires sending the book's text to Gemini exactly once and reusing that context for every later step via `previous_interaction_id` chaining, rather than re-sending the full text on each call (§4.3's cost-discipline requirement). The naive design is one chain per project. Running the actual reference notebook first — before writing any application code, per the brief's suggested workflow — showed that assumption is wrong: the *text* model conversation (book upload → style → characters → chapters) and the *image* model conversation (portrait setup → portrait 1 → portrait 2 → illustration setup → chapter illustration) are separate conversations against two different models. Character-to-illustration visual consistency comes from the *image* chain staying unbroken across all image calls in the project — not from re-uploading a previously generated portrait image as input to the illustration call, which was the initial (incorrect) assumption before reading the notebook closely.

This produced two columns on `Project`: `last_text_interaction_id` and `last_image_interaction_id`, each advanced independently and only after its respective Gemini call actually succeeds — so a failed step never corrupts the chain that a retry needs to resume from.

## 4. Optimistic locking (`@Version`) to prevent duplicate step execution

§4.3 requires that a refresh, a second browser tab, or a double-click during a running step must not fire the Gemini call twice — the UI should simply show the existing in-flight state. This is implemented with JPA's `@Version` column on `Project`, combined with an explicit `step_state == RUNNING` check performed before flipping the state to `RUNNING` and calling `saveAndFlush()` inside the same transaction. A concurrent request racing against the same row either observes `RUNNING` already set (rejected with `409 STEP_ALREADY_RUNNING`) or loses the optimistic-lock race on save and is translated into the same 409. This was verified directly by firing two near-simultaneous requests against the same project and confirming exactly one `RUNNING` transition ever occurs. Cost: `ObjectOptimisticLockingFailureException` has to be caught explicitly and mapped to the domain error, or it leaks out as a raw 500.

## 5. Stale-step recovery threshold: 120 seconds, not the demo's 8 seconds

`app-demo.html`'s stuck-step detection uses an 8-second threshold, because its simulated steps take about 2 seconds each. Real Gemini calls do not: text calls typically run 5-15 seconds, and image calls routinely took 15-25+ seconds once quota allowed them to run at all. An 8-second threshold would falsely flag steps that are simply still working, which would actively encourage users to retry (and re-bill) calls that hadn't failed. We used a 120-second threshold instead (`StepStaleChecker`), checked lazily in two places: when serving `GET /projects/{id}` (surfaced to the frontend as a `stale: true` flag so the UI can offer a recovery affordance), and inside the retry endpoint itself, which auto-recovers a stranded `RUNNING` step into `FAILED` before immediately re-dispatching the correct next step based on `status`. No background scheduler or cron sweep was added — staleness is only evaluated on read or on retry, which is simpler and sufficient at this scale, at the cost of a stranded project sitting silently until someone actually opens it or calls retry.

## 6. Retry is a single dispatcher endpoint, not one per step

Rather than exposing five near-identical `/steps/{step}/retry` endpoints, `POST /projects/{id}/steps/retry` reads `project.status` and re-invokes exactly the step that should run next: `CREATED -> retry Style`, `STYLE_SET -> retry Characters`, and so on through `CHAPTERS_GENERATED -> retry Illustrations`. This removes any possibility of a client asking to retry the wrong step — the server is the single source of truth for "what happens next," which also simplifies the frontend (one button, no step-specific retry logic). Cost: the dispatcher is a switch statement that has to be extended every time a new pipeline step is added — an explicit trade-off toward "smallest thing that works now" over generality for steps that don't exist yet, acceptable given the brief explicitly bounds the pipeline to 5 fixed steps.

## 7. Character/chapter caps enforced in code, not just in the prompt

The brief states the 2-character / 1-chapter caps are hard requirements that bound API cost and must be enforced server-side, not just requested of the model. The first version of the generation prompts asked Gemini to "list at most 2 characters" / "at most 1 chapter" and initially treated that instruction as sufficient. It isn't — Gemini is not guaranteed to comply with a soft instruction, and trusting it would violate the brief's explicit requirement. The fix: always parse the *full* array Gemini returns, then apply `.stream().limit(MAX_CHARACTERS)` / `.limit(MAX_CHAPTERS)` in code before anything is persisted or used to trigger a downstream (billable) image call, regardless of how many items the model actually returned. This was verified with a unit test that mocks a 5-character Gemini response against a cap of 2, and asserts exactly 2 are persisted.

## Seed a default admin user on startup

Added `DataInitializer` (a `CommandLineRunner`) that creates one admin user
(`admin@bookstudio.com`) on first boot if it doesn't already exist, purely to
let a reviewer log in immediately without going through project creation from
a completely empty database. Idempotent by design — checked via
`findByEmail` before insert, verified with a unit test for both the
create-once and skip-if-exists paths.

## Where AI-generated output was wrong and had to be overridden

**Fabricated Maven artifact IDs.** An early `pom.xml` draft (produced by an AI coding assistant) included `spring-boot-starter-webmvc`, plus separate `spring-boot-starter-data-jpa-test`, `spring-boot-starter-webmvc-test`, `spring-boot-starter-flyway-test`, and `spring-boot-starter-security-test` dependencies — none of which exist in Maven Central. The actual Spring Boot convention is a single `spring-boot-starter-web` for MVC, and one `spring-boot-starter-test` that already bundles JUnit 5, Mockito, AssertJ, and MockMvc — there is no per-module "-test" split. This would have failed immediately at `mvn install` with "could not find artifact." Caught by checking each artifact ID against what's actually resolvable in the registry rather than trusting the generated list at face value.

**`background: true` assumed to work identically for image generation.** The reference notebook's Python SDK usage implied image calls could be issued the same way as text calls. The initial REST design mirrored that and used `background: true` plus polling `GET /interactions/{id}` for both text *and* image steps. The image model rejected this outright with a `400`: `"Model 'gemini-3.1-flash-lite-image' does not support background interactions."` This constraint isn't called out in the REST documentation and was only discovered by making the real call. Fixed by removing `background` and the associated polling loop entirely for image calls, and accepting that they block synchronously inside the `@Async` executor thread for the full 10-30+ second generation time — which turned out to be simpler than the polling code it replaced.

**JSON field naming silently wrong until a live 400.** The Gemini REST API expects `snake_case` field names (`previous_interaction_id`, `response_format`, `mime_type`); Java/Jackson defaults to `camelCase`. A global `PropertyNamingStrategies.SNAKE_CASE` `ObjectMapper` was configured first, on the assumption that wiring it into the `RestClient` bean's message converters would be sufficient — it wasn't; the converter didn't actually take effect for that bean in practice, and requests kept serializing `mimeType` instead of `mime_type`. This only surfaced via a real `400 Unknown parameter 'input[0].mimeType'. Did you mean 'mime_type'?` response — the bug was invisible until an actual API call was made. Replaced the global-strategy approach with explicit `@JsonProperty("mime_type")` annotations on every field of every Gemini DTO. More verbose, but it doesn't depend on converter wiring being correct, and a missing annotation is now a compile-time-adjacent, line-level omission rather than a silent runtime failure.

**Prompt-only cap enforcement, without a code-level limit.** Covered in full in decision 7 above — the shorthand version: the model was initially trusted to self-limit its own output to the required caps, which the brief explicitly disallows.

## Known limitation: image generation could not be fully verified end-to-end

Style, Characters, and Chapters steps were verified repeatedly against the real Gemini API during development. Portraits and Illustrations were implemented following the same verified pattern (same client, same chaining logic, same error handling) and were exercised against the real API — but the Google account used for this submission hit a persistent `limit: 0` free-tier restriction on every image model tried (`gemini-3.1-flash-lite-image`, `gemini-2.5-flash-preview-image`, `gemini-2.5-flash-image`). This was confirmed with a direct `curl` request, fully independent of the application code, which ruled out an application-level bug. This is an account/billing-level constraint outside the application's control, not a design gap in the pipeline — the retry and stale-detection mechanisms for these two steps were validated through simulated failures (`GeminiPipelineServiceTest`, mocked Gemini client) rather than a live end-to-end image run.
